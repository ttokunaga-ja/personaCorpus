# 対象の計画行の原稿を1件ずつ書く

指示の「読むファイル」に示されたパスを用途に従って開いてください。資料の本文は指示に埋め込まれていません。事実の台帳は、対象の行（計画前は依頼）に関係する案件・出来事の見出しを検索し、該当する部分を読んでください。
AGENTS.md、SPEC.md、runbooks/PRODUCTION.md の「原稿」、runbooks/REVIEW.md の「原稿のレビュー」、persona 定義、事実の台帳、テンプレート一覧を読んでください。BATCH_CONTEXT の rows だけを対象に、中身を全部書いた Markdown の原稿を作ります。全体計画は文脈として使います。成果物の成形はしません。

原稿の置き場所は `sources/<persona>/<計画のパス>.md` です。例えば計画のパスが `Documents/月次/調整.xlsx` なら `sources/<persona>/Documents/月次/調整.xlsx.md` です。先頭に次の設定を置きます。

```yaml
---
path: Documents/月次/調整.xlsx
kind: 計画の「作り方」の値
author: その文書を書いた人物
derived_from:
---
```

`modified_by`（最終更新者。省略時は `author`）と `created`（作成日時。省略時は計画の日付）を任意で先頭設定に書けます。別の人が直した版や、前の版を上書き保存した文書では、この 2 つを書いてください。計画の日付は最終更新日時です。日時にタイムゾーンがなければ persona のタイムゾーン、日付だけなら正午として扱います。

先頭設定の `device`（任意）には、写真を撮ったカメラ・スマートフォンや、スキャンに使った複合機など、計画と persona の世界に合う機器名を書けます。アプリ名や制作の道具の名前は書きません。指定した値は成形後に `bin/stamp --device` に渡されます。機器の指定が不要な文書では省略します。

`author` は persona 本人とは限らず、社外から届いた文書はその相手です。`derived_from` は、**元が成果物として計画か people/<persona>/ にあるもの**（Office から出した PDF、手元の文書を印刷してスキャンしたもの、メールに添付した控え）だけに、その元の people/<persona>/ からの相対パスを書きます。その場合、本文には元との違い（押印、手書きの書き込み、スキャンの傾きなど。無ければ「違いなし」）だけを書き、元の原稿を読んで関係を確かめます。元が成果物でないもの（社外から紙で届いた文書のスキャンなど）は `derived_from` を空にして、本文に全文を書き、紙やスキャンの様子を末尾に書きます。scratch の中間ファイルを `derived_from` に書いてはいけません。

- **1 件ずつ、その人として書く**。計画の「内容」にある出来事・数値・結論を全文に入れ、その文書の種類として実務で使える中身と長さにします。調整表なら明細と差異の内訳、議事録なら出席者・決定事項・担当と期限、提案書なら金額と条件をそろえます。書き手の立場、相手との関係、言葉づかいを出し、言語は persona 定義に従います。
- **事実を合わせる**。人名、役職、組織、案件、金額、日付、文書番号、メールのスレッドを、persona 定義、事実の台帳、関連する過去の原稿と合わせます。関連の原稿は実際に読みます。台帳にない細部を決めたら最終出力に書き、台帳は変更しません。定義にない組織や案件は足しません。
- **判断の根拠**：評価表や確認票では、各判定を判断基準の必要な要素すべてと照合し、参照した記録のどの事実で満たすかを書きます。「説明した」だけから調整・合意まで済んだとせず、記録にない根拠を補って適合扱いしません。
- **型が要求する本文の項目**：型の README.md で表紙・副題・管理欄に入れる指定のある文書番号、版、宛先などは、台帳・計画の値を原稿の該当箇所に書きます。成形時の補完を前提に省略しません。
- **版とメール参照の照合**：初版・修正版がある場合、各版の日付時点で分かっていた事実を分け、後日の工程名や結論を初版へ混ぜません。メールを書き終えたら、固定された Message-ID を台帳・計画の該当箇所と文字単位で照合し、返信の In-Reply-To・References が元の値を参照することを確かめます。前回理由に識別子の不一致があれば、再生成した別の識別子で置き換えず、指定値へ合わせます。
- **文書**（DOCX、PDF、テキスト）：見出しと本文の全文、表の全内容を書きます。変更履歴・コメントは、誰がいつ何をどう直したかも書きます。本文の中に「【河野、7月10日 11:40、削除・取り消し線】」のような説明の注記を入れず、本文は直した後（または直す前）の文面にして、変更は本文の後の「## 変更履歴」の節に、種類（挿入・削除・コメント）、人物、日時、対象の文、新しい文の形で列挙します。成形がそれを Word の変更履歴・コメントにします。
- **表**（XLSX、CSV、TSV）：シートごとに見出し、全部の行、数式、注記を書きます。合計・差異は `=SUM(E7:E11)` のように数式で書き、範囲と計算が合うようにします。数十行以上の明細は、列の定義、行の作り方、合計が合う条件、代表の 10 行を書きます。本文・表・グラフ・関連文書の数値を合わせ、未確認の項目を 0 扱いしません。
  CSV・TSVで利用者に渡す必要がある備考は、計画に沿って表のどの行・列に入れるか明示します。照合用の合計や用途説明は表外に区別します。
- **スライド**：1 枚ごとにレイアウト、題、本文、表や図の中身、発表者のメモを書きます。
- **メール**：From、To、Cc、Date（人物のタイムゾーン）、Subject、Message-ID、返信の In-Reply-To と References、本文、引用、添付の名前を書きます。アドレスは persona 定義に従い、元メールと返信の時系列・引用を合わせます。Message-ID は、事実の台帳か計画にそのメールの値が書いてあれば、その値をそのまま使います（形がどうであっても変えません。ほかの原稿がその値を参照するためです）。書いてなければ、長いランダムな英数字列または UUID に `@送信元ドメイン` を付けて山括弧で囲んだ値にし、件名・案件名・人名など人が読める語をローカル部に使いません。事実の台帳・計画と、この指示の一般的な書き方が食い違うときは、台帳と計画に合わせます。返信の In-Reply-To と References は元メールの Message-ID をそのまま参照します。
- **グラフと図**：元の数値、軸、単位、凡例、題を書きます。
- **メールの添付と本文の区別**：今回添付するものと引用した前便の添付を区別します。添付を保存する場所や MIME への組込み方などの成形指示は、送信者の本文と分けます。相手への本文に「保存先：Documents/…」「本文への埋め込みなし」などの制作メモを入れません。実添付の扱いは `prompts/build.md` の「メール」「派生文書」に従います。
- **写真・手書き・スクリーンショット**：何がどう写っているか、読める文字は全部書きます。この段階で画像は生成しません。

フォント、色、余白などの書式は書きません。型が決めます。本文に合成の注記、制作用 ID、batch や割当、検査や評価の記述、「サンプル」「ダミー」などの断り書き、仮の文を入れません。コードは成果物にしません。

ID・日付・少数の値を差し替える量産スクリプトは禁止です。計画にない原稿を足しません。reasons がある行は、前回の原稿が不合格でした。その理由を解決する新しい原稿を同じ計画行から書き直してください。

書いてよい場所は、対象行に対応する `sources/<persona>/` の原稿と BATCH_CONTEXT の work 以下だけです。people、テンプレート、計画、台帳、persona、資料、他の計画行や受入済みの原稿は変更しません。一時物も指定された work 以下に置きます。stage・commit・push はしません。書けない行は作らず、理由を最終出力に書いてください。

実行専用の作業フォルダは BATCH_CONTEXT の work、レンダリング先は render です。他の実行の作業フォルダへ一時物を書きません。指定された review_output だけは指定先へ書きます。

BATCH_CONTEXT の missing_prerequisites は、対象行ごとに欠けている「先に要るもの」のパスを示します。不合格で破棄され原稿が無いものは、その行の計画の「内容」（破棄の印を除く）と事実の台帳をもとに、元の文書があるものとして書きます。引用が要るなら、計画と台帳にある範囲で書きます。欠けた原稿自体は作成せず、対象行だけを書いてください。

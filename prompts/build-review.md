# 成果物の見た目を制作とは別の実行でレビューする

指示の「読むファイル」に示されたパスを用途に従って開いてください。資料の本文は指示に埋め込まれていません。事実の台帳は、対象の行（計画前は依頼）に関係する案件・出来事の見出しを検索し、該当する部分を読んでください。
AGENTS.md、SPEC.md、runbooks/REVIEW.md の「見た目のレビュー」、persona 定義、計画、原稿、実際の型と見本を読んでください。BATCH_CONTEXT の rows の成果物を 1 件ずつ開きます。制作側のログ・最終出力・言い訳は読みません。中身の執筆し直しはせず、合格原稿が正しく形になっているかを判定します。

DOCX・XLSX・PPTX・PDF は `bin/render` で BATCH_CONTEXT の work 以下の render/ に画像化し、全ページを実際に見ます。画像は画像そのものを見ます。原稿・型と照らし、本文の抽出や表の数式・計算結果・内部プロパティも確認します。テキストやメールなども通常の読める形で開き、原稿との一致を確認します。画像化や抽出の成功だけで合格にはしません。

音声は実際に再生し、冒頭・中間・末尾と原稿の主要な発言の位置で、話者・内容・操作・経過時間を照合します。長い空白があれば前後を聴き、原稿の中断や操作で説明できるか確認します。形式・再生時間・波形だけで合格にしません。

音声入力を利用できることが明示されている実行でのみ、音声をモデルに渡します。非対応または対応不明の実行では、音声本体・切り出し・Base64をツールの出力や audio() でモデルに返しません。音声を送ると応答が HTTP 400 で途絶え、ほかの行の結果も失われます。実聴できない音声は判定TSVで reject・other とし、理由に「音声入力を利用できず実聴未了」と対象パスを記録します。成果物の欠陥を推定せず、同じ組のほかの行のレビューを完了します。

Office 文書を `bin/render`、LibreOffice、UNO で開く前に、対象ごとに BATCH_CONTEXT の work 以下へ通常のコピーを作り、そのコピーを開きます。LibreOffice や UNO を直接起動する場合は、プロファイルも work 以下に作ります。ZIP・XML の読み取りなど、隣に一時ファイルを作らない方法では元の文書を直接確認できます。

runbooks/REVIEW.md の見た目の 6 観点をすべて確認します。V1〜V5 の具体的な不適合は reject にし、V6 の内部情報の食い違いは batch 全体の所見にします。

1. 原稿との一致：内容の抜け・変更・追加がないか。派生文書は元と指定された違いを再現しているか。表の数式が値に置き換わらず、結果にエラーや原稿と違う値がないか。
   メールで原稿が実ファイルの添付を指定するときは、送信控えのMIMEパートを復号し、指定された保存版とバイト単位で比較します。不一致はV1として、添付名と差の内容を記録します。 添付0件の返信も本文を復号し、署名・引用の後まで読みます。原稿で成形用に分けた添付指定（例：Attachments: none）が受取人の本文に出ていればV1です。
2. 型：自社・社外それぞれの正しい型か。必須の管理欄は追加シートでもラベル・値が揃い、表題への置換や印刷範囲からの脱落がないかを型・原稿と照合する。型の空の行・仮の欄が残っていないか。原稿に未記入の指定がある欄は、レンダリングで欄名の直後を読み、指定語「空欄」が値として印刷されていたらV2とする。個人メモなど型なしが自然なものは除く。
3. 崩れ：文字のはみ出し・重なり・切れ、不適切な列幅、空白ページやスライド、文字化け・豆腐がないか。
4. 文書らしさ：スライドの表や図がただの箇条書きになっていないか。証明書や請求書に発行者・日付・番号・押印や署名の欄など必要な要素があるか。スキャンは紙のスキャンに、スクリーンショットは画面に見えるか。HTML はブラウザで表示し、入力欄・ボタン・タブが部品として見えるか（「検索欄：…［検索］」「タブ：概要｜履歴」のような説明の文字は破棄）。Word の修正は本物の変更履歴かコメントか（本文に「【…、削除・取り消し線】」「【…、赤字の挿入】」のような注記が印刷されていれば、原稿どおりでも破棄）。
図面は本文と別紙を含め、作図者向けの指示が印刷されていればV4です。同じ文章が元図にあっても返却スキャンでの露出を指摘します。寸法確認用の写真では目盛を拡大し、数値間の細分が測定単位と整合するかを複数区間で確認します。手書き資料は見出しも拡大し、紙質や筆記方法など原稿の描写指定が筆者の言葉として写り込んでいればV4とします。

筆跡の比較が文書の用途に含まれる場合は、原稿と読み合わせの記録が指定する字を原寸で並べます。同筆の比較字、別人の裏書、判読を妨げた紙の筋など、読み手が根拠にした特徴を実画像で探します。活字を拡大・太字化して別筆を表している場合や、判断に使った特徴を画像で確かめられない場合は、その箇所をV4・V5として記録します。送付控えの実添付にも同じ欠陥が残るかを確かめます。

5. 画像：生成と分かる崩れた文字や形がないか。写真やスキャンに原稿の文面や対象が実際に写っているか。写真に写る土地柄が persona の設定（国・地域・季節）に合っているか（日本なら、車両の形とナンバー、建物の材料、標識・表示の文字、設備の型）。生成画像は北米風の車両・建物になりやすい（p17 の海田の荷さばき写真に、ロールアップ扉と赤白の反射帯の北米型トラック、ブロック積みの壁が写ったまま受入された前例がある）。合わなければ V5。図に軸・単位・凡例があるか。
6. 内部情報：変更履歴・コメントの人物と日時は原稿の指定に、文書プロパティの作成者は `author`、最終更新者は `modified_by`（省略時は `author`）、作成日時は `created`（省略時は計画の日付）、最終更新日時は計画の日付に照合します。原稿に指定のない細部は不合格の理由にしません。PDF と画像には最終更新者の欄がないので、作成者と日時だけを見ます。写真は撮影日時（計画の日付）だけを見ます。日時にタイムゾーンがなければ persona のタイムゾーン、日付だけなら正午として照合します。内部情報は `bin/stamp` がそろえ、作り直しても変わらないため、食い違いを見つけても成果物の reject 理由にせず、対象パス・フィールド・期待値・実測値を batch 全体の所見に書きます。

型そのものの欠陥（README.md の説明と実物の食い違い、型自体の崩れ）は、個々の成果物の不合格にしません。型のとおりに成形された成果物は、その型の欠陥を理由に reject にせず、他の観点を満たしていれば pass にします。型の欠陥は最終出力の batch 全体の所見として報告します。

独立監査後の見た目の再レビューでは、対象batchの監査報告と統括の判断記録があれば、対象行への指摘を開き、現物で解消を確かめます。前回passでも、監査で確認された不適合は再レビューの対象です。

再レビューでは、まず BATCH_CONTEXT の reasons と previous_verdicts を読み、前回の不合格理由が解消されたかを実物で確認します。前回 pass だった行が前回と同じ状態なら、新しい理由で reject にしません。

判定は pass または reject だけです。音声の実聴未了は上記の other に記録します。成果物自体を reject にする場合は、該当する観点と問題の具体的な箇所を示します。抽象的な懸念や好みだけで reject にしません。具体的な問題が確認でき、「直せば使える」状態なら reject です（V6 と型そのものの欠陥は所見として扱います）。自動検査の通過や件数を合格理由にしません。合格にも何を確かめたかを 1 文で具体的に書きます。不合格はどの観点のどの箇所かを示します。

CSV・TSVは表として開き、見出し、各列の意味、原稿が指定した明細・備考と照らします。表外の説明を空欄で埋めて1行にしたものはV1です。
表外にある検算や使い方は照合に使います。これを独立した末尾行として要求しません。計画が表内に求める注記や合計が欠けた場合は、該当する行・列を示します。
BATCH_CONTEXT の review_output に、ヘッダなし TSV（people/<persona>/ からの相対パス、pass/reject、観点、理由）の 4 列を、対象の全行について 1 件 1 行で書いてください。観点は不合格なら `V1`〜`V5` の該当する番号、該当がなければ `other`、合格なら空にします。理由にタブ・改行を含めません。最終出力には見た目の所見（V6 の内部情報の食い違いを含む）とレンダリングの場所に加え、必ず「型の欠陥」の欄を設けてください。欠陥があれば型の名前（ファイル名）と欠陥の具体的な内容を 1 件ずつ書き、なければ「なし」と書きます。この欄は個々の成果物の判定 TSV と分けます。

レビューは読み取り専用です。書いてよいのは 指定された review_output と BATCH_CONTEXT の work 以下のレンダリングとレビュー用の一時物だけです。原稿、成果物、計画、台帳、型、persona、資料を変更せず、修正も削除もしません。stage・commit・push はしません。

実行専用の作業フォルダは BATCH_CONTEXT の work、レンダリング先は render です。他の実行の作業フォルダへ一時物を書きません。指定された review_output だけは指定先へ書きます。

印刷された用紙に手書きで記入してスキャンしたものは、印刷部分（社名、罫線、項目名）が型の用紙と同じで、記入内容が原稿どおり読めれば合格です。手書きの文字の位置や大きさ、スキャンのむらを理由に破棄にしません。

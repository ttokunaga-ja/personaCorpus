# 成果物の見た目を制作とは別の実行でレビューする

AGENTS.md、SPEC.md、runbooks/REVIEW.md の「見た目のレビュー」、persona 定義、計画、原稿、実際の型と見本を読んでください。BATCH_CONTEXT の rows の成果物を 1 件ずつ開きます。制作側のログ・最終出力・言い訳は読みません。中身の執筆し直しはせず、合格原稿が正しく形になっているかを判定します。

DOCX・XLSX・PPTX・PDF は `bin/render` で BATCH_CONTEXT の scratch 以下の render/ に画像化し、全ページを実際に見ます。画像は画像そのものを見ます。原稿・型と照らし、本文の抽出や表の数式・計算結果・内部プロパティも確認します。テキストやメールなども通常の読める形で開き、原稿との一致を確認します。画像化や抽出の成功だけで合格にはしません。

runbooks/REVIEW.md の見た目の 6 観点をすべて適用し、1 つでも当てはまれば reject にします。

1. 原稿との一致：内容の抜け・変更・追加がないか。派生文書は元と指定された違いを再現しているか。表の数式が値に置き換わらず、結果にエラーや原稿と違う値がないか。
2. 型：自社・社外それぞれの正しい型か。型の空の行・仮の欄が残っていないか。個人メモなど型なしが自然なものは除く。
3. 崩れ：文字のはみ出し・重なり・切れ、不適切な列幅、空白ページやスライド、文字化け・豆腐がないか。
4. 文書らしさ：スライドの表や図がただの箇条書きになっていないか。証明書や請求書に発行者・日付・番号・押印や署名の欄など必要な要素があるか。スキャンは紙のスキャンに、スクリーンショットは画面に見えるか。
5. 画像：生成と分かる崩れた文字や形がないか。写真やスキャンに原稿の文面や対象が実際に写っているか。図に軸・単位・凡例があるか。
6. 内部情報：変更履歴・コメントの人物と日時、文書プロパティの作者・日時が原稿と計画に合うか。アプリ名はその人物が使う普通のアプリとして自然で、制作の道具の名前や制作した実時間が残っていないか。

型そのものの欠陥（README.md の説明と実物の食い違い、型自体の崩れ）は、個々の成果物の不合格にしません。型のとおりに成形された成果物は、その型の欠陥を理由に reject にせず、他の観点を満たしていれば pass にします。型の欠陥は最終出力の batch 全体の所見として報告します。

判定は pass または reject だけです。迷ったら reject。「直せば使える」は reject です。自動検査の通過や件数を合格理由にしません。合格にも何を確かめたかを 1 文で具体的に書きます。不合格はどの観点のどの箇所かを示します。

BATCH_CONTEXT の review_output に、ヘッダなし TSV（people/<persona>/ からの相対パス、pass/reject、観点、理由）の 4 列を、対象の全行について 1 件 1 行で書いてください。観点は不合格なら `V1`〜`V6` の該当する番号、該当がなければ `other`、合格なら空にします。理由にタブ・改行を含めません。最終出力には見た目の所見とレンダリングの場所に加え、必ず「型の欠陥」の欄を設けてください。欠陥があれば型の名前（ファイル名）と欠陥の具体的な内容を 1 件ずつ書き、なければ「なし」と書きます。この欄は個々の成果物の判定 TSV と分けます。

レビューは読み取り専用です。書いてよいのは BATCH_CONTEXT の scratch 以下の指定された review_output、レンダリングとレビュー用の一時物だけです。原稿、成果物、計画、台帳、型、persona、資料を変更せず、修正も削除もしません。stage・commit・push はしません。
